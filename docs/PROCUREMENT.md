# Закупки и поставки

## Схема и денежные значения

Миграция `2026_11_11_000002_create_procurement` создаёт ровно пять таблиц:

- `suppliers`: организация, название, контактное лицо, телефон, email, необязательный ИНН, комментарий, активность и даты.
- `purchase_orders`: организация, поставщик, склад назначения, автор, статус, валюта, итог NUMERIC(24,2), комментарий, UUID запроса и его внутренний hash.
- `purchase_order_items`: организация, заказ, товар, заказанное/полученное количество, закупочная цена NUMERIC(12,2). `line_total` — GENERATED ALWAYS STORED NUMERIC(24,2), произведение количества на цену. Один товар встречается в заказе один раз.
- `goods_receipts`: организация, заказ, автор, статус, комментарий, подтвердивший пользователь и confirmed_at TIMESTAMPTZ, UUID запроса и hash.
- `goods_receipt_items`: организация, документ и строка заказа, товар, принятое количество, постоянный UUID складской операции и ссылка на созданное складское движение.

Составные PostgreSQL foreign keys запрещают связи разных организаций. Строка приёмки обязана принадлежать тому же заказу, что её документ, и тому же товару, что строка заказа. Quantity > 0, received_quantity находится между 0 и заказанным количеством. Уникальные индексы защищают от дублей строк/UUID. В существующую `stock_movements` добавлен только уникальный индекс `(organization_id,id)` для составного FK приёмки; новые остатки нигде не хранятся.

Все цены/суммы API закупок — **десятичные строки в основных денежных единицах**, например `"12.34"`, не JSON float и не price_minor. Каталог и API размещений сохраняют прежние целые price_minor. Закупочная цена не меняет цену продажи товара. Максимальная закупочная цена 9999999999.99; количество 1…2147483647; до 100 разных товаров в заказе. Суммы считает PostgreSQL NUMERIC, предварительный расчёт во Vue использует BigInt. Сумма заказа сохраняется по SUM сгенерированных сумм строк; клиент не может назначить итог или полученное количество.

## Состояния

Заказ создаётся в `draft` (черновик), редактируется только в этом статусе. PATCH передаёт весь состав черновика и обязательные поля шапки. `/order` переводит его в `ordered` (заказана); внешней отправки поставщику нет. Подтверждённые приёмки переводят заказ в `partially_received` и затем `received`. Неполученный остаток draft/ordered/partially_received можно отменить: статус `cancelled`, все черновики приёмок отменяются. Уже полученные товары, движения и подтверждённые документы сохраняются. Полученный заказ отменить нельзя.

Приёмка создаётся как `draft` и **не меняет склад**. Количество можно задать для всех товаров или только для части. Разрешено несколько черновиков приёмки: они не резервируют товары и не уменьшают остаток к получению. При подтверждении остаток к получению проверяется заново; устаревший документ с завышенным количеством отклоняется. Его можно отредактировать или отменить. Нулевые строки во Vue не включаются в документ.

`/confirm` переводит документ в `confirmed`, `/cancel` — непроведённый документ в `cancelled`. Подтверждённый документ нельзя редактировать или отменять. PostgreSQL-триггеры также запрещают UPDATE/DELETE подтверждённых документов и их строк. Для исправления проведённого хозяйственного факта нужен отдельный последующий процесс, а не переписывание документа. Времена подтверждения возвращаются в UTC ISO 8601; часовой пояс сохраняется явно независимо от timezone PostgreSQL-сессии.

Поставщика без закупок можно удалить; при наличии заказов DELETE возвращает 409, вместо удаления используется is_active=false. Неактивные поставщики и склады не выбираются для новых заказов. Исторические документы доступны; приёмка на отключённый склад отклоняется существующим складским сервисом.

## Транзакции и повторы

`ProcurementService` содержит бизнес-операции. Подтверждение блокирует заказ FOR UPDATE, затем документ и строки. Все подтверждения одного заказа сериализуются, в том числе разных частичных приёмок. Каждая строка проводится через существующий `StockOperationService` с типом receipt, постоянным UUID, текущим пользователем и комментарием с номерами документа и закупки.

Складские остатки/движения, received_quantity, статус заказа, ссылки приёмки на движения и её подтверждение сохраняются в одной внешней транзакции PostgreSQL. Вложенные транзакции складского сервиса участвуют в ней. Ошибка любой строки откатывает весь документ. Строки проводятся в порядке product_id для согласованного порядка блокировок; исходные ограничения складского сервиса сохранены.

Повтор `/confirm` для уже подтверждённого документа возвращает 200 и meta.replayed=true без новых движений. Создание заказа и черновика приёмки требует request_id UUID: первый запрос — 201, повтор с тем же нормализованным составом и автором — 200 с прежним документом, другие данные с тем же UUID — 409. Ключи действуют в пределах организации. Во Vue UUID сохраняется при сетевой ошибке, изменённые поля означают новый запрос; после закрытия формы начинается новый запрос.

## API

Префикс `/api/v1`, Sanctum, существующий tenant scope и InventoryPolicy. Пользователь должен состоять в организации. Клиент не может передать организацию, автора, подтвердившего пользователя, время, статус или складские движения. Чужие ID в телах отклоняются, чужие документы по URL дают 404.

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET / POST | /suppliers | Список / создание поставщика |
| GET / PATCH / DELETE | /suppliers/{supplier} | Просмотр / изменение / удаление неиспользуемого |
| GET / POST | /purchase-orders | Список / создание черновика |
| GET / PATCH | /purchase-orders/{purchaseOrder} | Детали / полная замена черновика |
| POST | /purchase-orders/{purchaseOrder}/order | Отметить заказанной |
| POST | /purchase-orders/{purchaseOrder}/cancel | Отмена неполученного остатка |
| GET / POST | /goods-receipts | Список / создать документ без оприходования |
| GET / PATCH | /goods-receipts/{goodsReceipt} | Документ / изменение черновика |
| POST | /goods-receipts/{goodsReceipt}/confirm | Атомарно оприходовать |
| POST | /goods-receipts/{goodsReceipt}/cancel | Отмена черновика |

Пагинация: page, per_page=1…100, default 20. Поставщики: search по названию, контактному лицу, телефону, email и ИНН; is_active. Закупки: search по номеру, поставщику, названию/SKU товаров; status, supplier_id, warehouse_id. Приёмки: search по номеру, поставщику и товарам; status, purchase_order_id, supplier_id, warehouse_id. Списки документов — новые сверху; поставщики — по названию и ID.

Создать заказ:

```json
{
  "request_id": "5fc703f6-511b-4b32-9321-1632cb1f450a",
  "supplier_id": 1,
  "warehouse_id": 1,
  "currency": "RUB",
  "comment": "Плановая закупка",
  "items": [{"product_id": 10, "quantity": 10, "unit_price": "12.34"}]
}
```

После `/order` создать частичную приёмку (используется ID строки заказа, а не ID товара):

```json
{
  "request_id": "3fcb728e-9390-44a1-ad54-3c21f8cf86c0",
  "purchase_order_id": 1,
  "comment": "Первая партия",
  "items": [{"purchase_order_item_id": 5, "quantity": 4}]
}
```

Затем POST `/goods-receipts/{id}/confirm` без тела. Остатки и документы проверяются сервером; создание самого документа ничего не приходует. Полная схема запросов и ответов находится в [openapi.json](openapi.json).

## Frontend и проверки

- `/app/purchases`: вкладки «Закупки», «Поставщики», «Приёмки», поиск, фильтры, пагинация и формы.
- `/app/purchases/:id`: шапка, цены/суммы, заказано/получено/осталось, редактирование черновика, заказ/отмена, создание частичной или полной приёмки, переход к документам.
- `/app/purchases/receipts/:id`: документ, редактирование/подтверждение/отмена черновика, авторы, время и ссылки на реальные складские движения.

Тема, таблицы, ResourcePicker, состояния и авторизованный Axios-клиент используются из существующего интерфейса. Остальные разделы не переработаны. Внешних интеграций и отдельной системы остатков нет.

Backend: `php artisan test`. ProcurementTest проверяет точные суммы (включая значения выше Number.MAX_SAFE_INTEGER), черновики, частичные/полные приёмки, откаты, историю, повторы, ограничения состояний, tenant isolation, права, валидацию, неактивный склад и UTC-время. ProcurementConcurrencyTest использует два независимых PHP-процесса и реально пересекающиеся PostgreSQL locks: повтор одного документа, превышение остатка разными приёмками, успешное завершение двумя частичными приёмками.

Frontend: `npm.cmd run typecheck`, `npm.cmd run build`, `npm.cmd run lint`, `npm.cmd test`. Браузерный цикл: `npm.cmd run test:e2e:procurement`. Он использует отдельные Laravel/Vite процессы и только `.env.testing` с PostgreSQL-базой, имя которой заканчивается `_test`, выполняя migrate:fresh до/после. Его нельзя запускать параллельно с backend- или складскими браузерными тестами на той же базе. Проверяет весь цикл, CRUD поставщиков, потерю ответа подтверждения и безопасный повтор, частичную/полную приёмку и мобильную ширину.

Миграция: `php artisan migrate`. Рабочая база не заполняется фиктивными поставщиками, закупками или приёмками; тестовые данные создаются только в тестовой БД.

Итог проверки реализации: полный backend-набор — 66 тестов, 556 проверок, успешно; TypeScript, production build и ESLint — успешно; frontend unit-тесты — 6 успешно. Браузерные сценарии закупочного и существующего складского циклов — оба успешно. Проверены потеря ответа после проведения и повтор без двойного оприходования. Миграция применена к локальной рабочей базе; после применения во всех пяти новых таблицах подтверждено 0 строк, демонстрационные данные не добавлялись.

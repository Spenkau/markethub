# Сквозной путь и обучение MarketHub

## Бизнес-путь

Чек-лист «Начало работы» находится на обзоре `/app`. `GET /api/v1/onboarding/checklist` каждый раз проверяет реальные записи **текущей доступной организации**, с существующими tenant scopes и Gates. Этапы независимы, их не нужно проходить в заданном порядке:

1. Организация — у пользователя есть действующая выбранная организация/членство.
2. Склад — создан хотя бы один склад.
3. Товар — есть товар каталога.
4. Поставщик — есть поставщик.
5. Закупка — есть заказ поставщику.
6. Первая поставка — есть **подтверждённая** приёмка, в том числе частичная. Черновик приёмки этап не завершает.

Созданные, затем отключённые записи и отменённый заказ остаются фактом выполнения этапов создания. Проверка не читает прогресс экскурсий, localStorage или произвольные флаги «готово». При возвращении на обзор либо переключении организации этапы рассчитываются заново. Сворачивание чек-листа — личная настройка пользователя, она не меняет этапы.

Минимальное создание организации добавлено, поскольку раньше API позволял только читать и выбирать организации: POST `/api/v1/organizations`, имя и request_id UUID. Создатель получает членство, новая организация становится активной. Повтор с тем же ключом/именем от того же участника возвращает прежнюю организацию; конфликтующие данные — 409. Нельзя назначить другого пользователя или получить чужую организацию через ключ.

Контекстные переходы:

| Откуда | Куда |
| --- | --- |
| Сохранённый склад | Новый товар либо закупка со складом |
| Сохранённый товар | Физические остатки товара либо закупка с товаром |
| Карточка товара | Закупка с выбранным товаром |
| Сохранённый/активный поставщик | Закупка с выбранным поставщиком |
| Новая закупка | Её детали и дальнейшее изменение статуса |
| Заказанная/частично полученная закупка | Создание частичной либо полной приёмки |
| Подтверждённая приёмка | `/app/stocks?warehouse_id=...` |
| Складская позиция | Карточка товара, история или закупка с товаром и складом |
| Движение от приёмки | Связанный документ `/app/purchases/receipts/:id` |

Для открытия предзаполненной закупки используется `/app/purchases?create=purchase&supplier_id=...&warehouse_id=...&product_id=...`. Все параметры необязательны, кроме create. Клиент сначала читает сущности через существующий авторизованный API; чужой или удалённый ID не превращается в фиктивное подтверждение успеха. Форма открывается без создания заказа. Маркер create удаляется после открытия. Статусы документов определяют доступные действия; для устаревшей приёмки без доступного остатка проведение не предлагается.

Связанный документ движения берётся из реальной `goods_receipt_items.stock_movement_id`, а не извлекается из комментария. GET `/api/v1/stock-movements` дополнен nullable document `{type:'goods_receipt',id,purchase_order_id}`. Обратная связь загружается заранее и сохраняет tenant scope.

## Модуль экскурсий

`frontend/src/features/onboarding/` — отдельный frontend-модуль без новых библиотек и тяжёлых шаблонов:

- `config/tours.ts` — единственный реестр описаний, версий, шагов и триггеров.
- `types.ts` — TourDefinition, TourStep, прогресс и настройки.
- `composables/useProductTour.ts` — один Pinia store управления сценарием, сохранением и маршрутами.
- `services/tourProgress.ts` — авторизованный API для прогресса; `geometry.ts` — безопасное размещение подсказки.
- `components/TourHost.vue` — интеграция с маршрутом и безопасными моментами показа.
- `TourOverlay.vue` и `TourTooltip.vue` — затемнение, подсветка, карточка, focus trap и восстановление фокуса.
- `TourLauncher.vue` — компактная ссылка «Как это работает?».
- `GettingStarted.vue` — отдельный реальный бизнес-чек-лист.

Центр «Помощь и обучение»: `/app/help`, доступен в боковом меню. Там все доступные экскурсии, их описание и статус текущей версии, запуск, продолжение, повтор и настройка автоматических предложений.

Базовые экскурсии:

| ID | Название | Автоматический повод |
| --- | --- | --- |
| welcome | Первое знакомство с MarketHub | Первое безопасное посещение кабинета |
| products | Товары и единый каталог | Первое посещение `/app/products` |
| warehouses | Склады и остатки | Первое посещение `/app/stocks` |
| suppliers | Поставщики | `/app/purchases?tab=suppliers` |
| purchases | Закупки и поставки | `/app/purchases` без другой вкладки |
| marketplaces | Маркетплейсы и размещения | `/app/marketplaces` |

Автоматический повод означает **ненавязчивое предложение**, а не самопроизвольное модальное обучение. У пользователя всегда остаётся выбор начать, отложить или отключить. Сценарии явно объясняют отсутствие внешних интеграций и различие физического остатка/остатка размещения. Экскурсии не сохраняют товары, склады или документы.

## Как добавить экскурсию

1. Добавьте стабильный атрибут на существующий элемент, например `data-tour="product-list"`. Не используйте случайные CSS-классы, номера строк или сложные DOM-пути.
2. Добавьте объект в массив `tours` в `frontend/src/features/onboarding/config/tours.ts`:

```ts
{
  id: 'catalog-short-help',
  title: 'Короткая помощь по каталогу',
  description: 'Что показывает список товаров.',
  version: 1,
  trigger: { type: 'first-visit', route: '/app/products', snoozeHours: 24 },
  steps: [
    {
      id: 'list',
      route: '/app/products',
      target: '[data-tour="product-list"]',
      title: 'Ваш каталог',
      description: 'Здесь существующие товары выбранной организации.',
      placement: 'bottom',
    },
    {
      id: 'create',
      target: '[data-tour="create-product"]',
      title: 'Добавить карточку',
      description: 'Откройте форму после завершения экскурсии.',
    },
  ],
}
```

3. Для ручного сценария просто не задавайте trigger. Для первого знакомства используется trigger.type='first-login'. Для разделов — first-visit с точным route.path и необязательным query; значение null в query означает отсутствие параметра. Первый маршрут шага может включать query, например `/app/stocks?tab=warehouses`.
4. Если нужен компактный запуск в разделе, используйте `<TourLauncher tour-id="catalog-short-help" />`. Центр обучения подхватит сценарий из реестра автоматически.
5. При содержательном изменении увеличьте version. Старый прогресс сохранится отдельно, текущая версия сможет быть предложена снова. Отключённая пользователем автоматика продолжит соблюдаться.
6. Запустите проверки frontend и браузерные тесты обучения.

Идентификаторы туров: 1–80 букв/цифр/дефисов/подчёркиваний. ID шага — до 100 таких символов. Версия 1…1000000, не более 200 шагов. Новой экскурсии не нужны правки движка, новые backend endpoints или копия реестра на PHP: backend хранит пользовательские метаданные, frontend знает сценарии.

Для объяснения полей модальной формы шаг может иметь `reveal: {target:'[data-tour="create-purchase"]',close:'[data-tour="close-purchase-form"]'}`. Это **только открытие пустого UI**, при необходимости. Движок помнит открытые им формы и закрывает их при переходе/завершении. Никогда не указывайте в reveal кнопки сохранения, проведения, списания или другой бизнес-операции. Если пользователь уже работает с формой, запуск нового сценария отклоняется с пояснением.

## Поведение и доступность

- Один активный сценарий, одна карточка предложения.
- Автопредложение не показывается во время видимой формы/модального окна, фокуса в поле или незавершённого изменяющего API-запроса.
- Автопредложения выдерживают на сервере и клиенте паузу 15 минут после последнего предложения или запуска; также проверяются дата допустимого показа и глобальный флаг автоматики. Ручной запуск этой паузой не ограничен. Неотвеченное предложение повторно допустимо не раньше суток; «Напомнить позже» по умолчанию откладывает на 24 часа, интервал конфигурируется в trigger.snoozeHours (1…720).
- Completed/skipped той же версии не предлагаются автоматически. In_progress после перезагрузки предлагается продолжить вручную в центре обучения, без нового модального запуска. Snoozed возобновляется с сохранённого шага при ручном продолжении; повторный запуск явно начинает сначала.
- После перехода на другой маршрут вне экскурсии она приостанавливается; записанный шаг остаётся. Escape, крестик и «Пропустить» закрывают её со статусом skipped. «Напомнить позже» сохраняет snoozed. При завершении карточка закрывается после подтверждения сохранения сервером; при ошибке доступен повтор.
- Ожидание элемента ограничено 2,5 секундами; ожидание стабилизации геометрии также ограничено. Если элемент отсутствует, карточка объясняет причину и позволяет продолжить/закрыть без подсветки. Если элемент слишком велик для экрана и рядом нет места, подсказка показывается без перекрывающей подсветки.
- Маршруты открываются через Vue Router, элементы прокручиваются в область видимости. Подсказка выбирает свободную сторону и ограничена краями viewport.
- Есть клавиатурный Tab/Shift+Tab внутри карточки, видимый focus, Escape и восстановление фокуса после закрытия. Прокрутка без анимации и CSS учитывают prefers-reduced-motion.
- Сбой сохранения не удерживает пользователя в экскурсии: закрытие всегда доступно, ошибка объясняется. Личный прогресс не хранится в localStorage/sessionStorage.

## Backend и хранение

Миграция `2026_11_11_000003_create_user_onboarding`:

- Новая `user_tour_progress`, уникальность `(user_id,tour_id,version)`, статус, ID/индекс шага, последнее начало, последнее предложение, завершение и next_eligible_at; даты TIMESTAMPTZ.
- В `users`: `tour_auto_start` default true, `onboarding_collapsed` default false. Ранее подходящей таблицы настроек не было; отдельная таблица общих настроек не создавалась.

Пользователь передаётся исключительно через Sanctum; организация и произвольный user_id в запросах запрещены. Запись защищена транзакцией с блокировкой текущего пользователя. Прогресс хранится для пользователя, не для организации, доступен на других устройствах. Статусы/время назначает сервис. Нельзя завершить незапущенный сценарий; повтор завершения идемпотентен, устаревшее advance после завершения отклоняется.

Новые endpoints:

| Метод | Endpoint | Назначение |
| --- | --- | --- |
| GET | /api/v1/onboarding | Личные настройки и прогресс всех версий |
| GET | /api/v1/onboarding/checklist | Реальные этапы выбранной организации |
| PATCH | /api/v1/onboarding/preferences | auto_start и/или checklist_collapsed |
| PATCH | /api/v1/onboarding/tours/{tour} | Событие прогресса текущего пользователя |
| POST | /api/v1/organizations | Создать организацию и членство |

Пример события прогресса:

```json
{"version":1,"action":"advance","step_id":"sku","step_index":2}
```

action: offer / start / advance / complete / skip / snooze. Для snooze необязателен snooze_hours (default 24). automatic=true у start требует серверного разрешения автоматики; явный ручной запуск работает и при отключённой настройке. Идентифицирующих другого пользователя параметров нет. Сервер не доверяет клиентскому status или датам.

## Проверки

Результат проверки реализации: backend — 74 теста / 632 проверки; frontend unit — 10 тестов; Playwright onboarding — 4 сценария. TypeScript, ESLint и production build проходят. OpenAPI JSON и все 255 ссылок на схемы проверены.

`php artisan test` — полный backend-набор, включая независимость чек-листа от туров, фактическое подтверждение приёмки, tenant isolation, пользовательскую изоляцию, версионность, snooze/отключение, UTC и валидацию. `npm.cmd run typecheck`, `npm.cmd run build`, `npm.cmd run lint`, `npm.cmd test` — frontend.

`npm.cmd run test:e2e:onboarding` запускает отдельный Laravel API и Vite, работает только с PostgreSQL `.env.testing` с окончанием имени `_test`, сбрасывая эту тестовую базу. Не запускайте его параллельно с другими тестами той же базы. Четыре сценария проверяют полный бизнес-путь с нулевой организации, первый автоматический повод/ручной запуск, reload/продолжение/другое устройство, snooze и настройку, новый сценарий и версию без изменения движка, отсутствие DOM, мобильную геометрию и focus, блокировку предложений при форме и отсутствие бизнес-запросов при экскурсиях.

Миграция применена к локальной рабочей базе. Фиктивные организации, товары, склады, закупки или приёмки в неё не добавлялись. Тестовые бизнес-данные создавались только в изолированной тестовой БД.

# Склады и остатки

## Схема и совместимость

Добавлены `warehouses`, `warehouse_stocks`, `stock_movements` миграцией `2026_11_11_000001_create_warehouse_inventory`. Старые таблицы, `marketplace_listings.stock_quantity`, `/api/v1/stocks` и XLSX `/api/v1/stocks/export` сохраняют прежнее назначение — остатки размещений на площадках. Складские данные не копируются из размещений и не складываются с ними.

- Склад: организация, название, уникальный в организации код, тип `own` / `marketplace`, активность, даты. Код нормализуется в верхний регистр. Склады отключаются через PATCH, физическое удаление API не предоставляет.
- Складской остаток: организация + склад + товар, целое quantity 0…2147483647. Уникальность тройки и составные внешние ключи запрещают дубли и связи между организациями. Запись появляется только при проведении операции, а не автоматически для каждого сочетания товара и склада.
- Движение: организация, склад, товар, пользователь, UUID operation_id, тип, изменение со знаком, количество до/после, комментарий, серверное occurred_at. Для перемещения — две записи с общим UUID. Внутренний request_hash проверяет повторный запрос и не выдаётся в API.
- PostgreSQL CHECK запрещает отрицательные остатки и некорректные движения. Триггер запрещает UPDATE/DELETE журнала даже при прямом SQL. В моделях также запрещено менять историю. Для исправления ошибки следует создать новую корректирующую операцию с комментарием.
- Внешние ключи сохраняют товары и пользователей, участвующих в истории. Товар в складском учёте нельзя удалить: его можно отключить. Названия товаров, складов и пользователей в выдаче истории — текущие названия связанных сущностей.

## API

Все endpoints используют Sanctum и текущую организацию. InventoryPolicy использует существующие правила доступа организации. Нет членства — 403; чужой склад по ID — 404; чужой склад/товар в операции — 422. Клиент не может назначить organization_id, user_id и дату движения.

| Метод | Endpoint | Назначение |
| --- | --- | --- |
| GET | /api/v1/warehouses | Склады с пагинацией |
| POST | /api/v1/warehouses | Создание |
| GET | /api/v1/warehouses/{warehouse} | Карточка |
| PATCH | /api/v1/warehouses/{warehouse} | Изменение и отключение |
| GET | /api/v1/warehouse-stocks | Физические остатки |
| GET | /api/v1/warehouse-stocks/summary | Показатели складского учёта |
| GET | /api/v1/stock-movements | Неизменяемая история |
| POST | /api/v1/stock-operations | Проведение операции |

Общие параметры: page, per_page (1–100, default 20), search (до 100 символов), sort, direction. Поиск остатков и истории идёт по названию/SKU товара, поиск складов — по названию/коду.

Склады: type=own|marketplace, is_active=0|1; sort=id|name|code|created_at.
Остатки: warehouse_id, product_id, stock=zero|low (low — 1–5); sort=id|quantity|updated_at.
История: warehouse_id, product_id, type=receipt|write_off|transfer|inventory, operation_id, date_from/date_to YYYY-MM-DD (включительно, серверный часовой пояс UTC); sort=id|occurred_at, по умолчанию occurred_at desc с ID как стабильным дополнительным ключом.
Сводка: positions, products, units, zero_positions, low_positions учитывают те же фильтры, что остатки. warehouses/active_warehouses всегда относятся ко всей организации. Во frontend карточки запрашивают сводку без фильтров и явно подписаны как общие.

Создание склада:

```json
{"name":"Основной склад","code":"MAIN-01","type":"own","is_active":true}
```

Проведение операции:

```json
{
  "operation_id": "df978c02-d40b-4cc6-ade2-c8bc1a64708c",
  "type": "transfer",
  "warehouse_id": 1,
  "destination_warehouse_id": 2,
  "product_id": 10,
  "quantity": 3,
  "comment": "Перемещение в резервный склад"
}
```

Для receipt и write_off quantity — положительное количество, destination_warehouse_id не передаётся. Для inventory quantity — фактический итоговый остаток (в том числе 0); разницу вычисляет сервис. Инвентаризация без изменения количества также сохраняет запись с дельтой 0. Для transfer нужны разные активные склады одной организации. Неактивные товары разрешены к учёту, неактивные склады — только к просмотру.

## Транзакции и повторные запросы

StockOperationService проводит всю операцию в DB::transaction с повтором транзакции при deadlock. PostgreSQL advisory lock по organization_id + operation_id сериализует повторы до создания первой строки. Затем склады блокируются по возрастанию ID, товар и строки остатков — FOR UPDATE. Согласованный порядок защищает встречные перемещения; блокировка складов также закрывает гонку создания первого остатка. Это намеренно простая стратегия: операции одного склада могут ожидать друг друга даже для разных товаров.

Недостаток товара, переполнение целого количества, неактивный склад или ошибка записи откатывают весь результат. Даже если исходный остаток уже был изменён, ошибка зачисления на целевой склад откатывает оба остатка и обе записи истории.

Успех: 201, `data.operation_id`, `data.movements`, `meta.replayed=false`. Повтор того же UUID с теми же нормализованными данными и тем же пользователем: 200, прежние движения, `meta.replayed=true`, количество повторно не меняется. Другие данные/пользователь с тем же UUID в организации: 409. UUID действуют в пределах организации и не истекают. Исправленный или новый хозяйственный факт требует нового UUID.

Vue генерирует UUID при создании формы и при изменении её полей, блокирует форму на время запроса и сохраняет ключ при сетевой ошибке. Повторное нажатие в той же форме после потери ответа не дублирует операцию. После закрытия формы/перезагрузки страницы начинается новая операция. Генерация UUID работает и на локальном HTTP markethub.test.

## Frontend

- `/app/stocks`: три вкладки «Остатки», «Склады», «История движений». Поиск, фильтр склада с серверным поиском/пагинацией, нулевые/низкие остатки, сортировка, фильтры истории по типу и датам; связь двух частей перемещения по UUID. Формы всех четырёх операций и управление складами.
- `/app/marketplace-stocks`: прежняя страница остатков площадок, включая фильтры и XLSX. Переходы из товаров, аккаунтов и показателей площадок ведут сюда.
- Карточка товара предоставляет отдельные ссылки на остатки площадок и физические складские остатки.
- Обзор сохраняет прежние KPI размещений и показывает отдельный блок физических складов из нового summary endpoint.
- Нет интеграций маркетплейсов, резервов, заказов клиентов и финансового учёта. Закупки реализованы отдельным модулем PROCUREMENT.md. Склад типа marketplace пока ведётся вручную.

## Проверки

Backend: `php artisan test`. WarehouseInventoryTest проверяет операции, фильтры, права, idempotency, ограничения PostgreSQL, неизменяемость истории и независимость marketplace-остатков. WarehouseConcurrencyTest запускает два отдельных PHP-процесса и проверяет, что оба реально ожидают PostgreSQL locks: первая запись с одинаковым UUID, конкурирующие списания, встречные перемещения.

Frontend: `npm.cmd run typecheck`, `npm.cmd run build`, `npm.cmd run lint`, `npm.cmd test`.

`npm.cmd run test:e2e` — существующий браузерный сценарий товаров, аккаунтов, остатков площадок, дашборда и мобильной навигации.

`npm.cmd run test:e2e:inventory` — отдельный браузерный сценарий через настоящий Laravel API. Он запускает API с APP_ENV=testing на 8001 и Vite на 5174. Используется исключительно PostgreSQL-база из `.env.testing`, имя которой обязано заканчиваться `_test`; до и после сценария выполняется migrate:fresh. Этот сценарий нельзя запускать одновременно с backend-тестами, использующими ту же тестовую БД. Он проверяет создание складов, потерю ответа после успешного поступления и безопасный повтор, недостаток товара, списание, перемещение, инвентаризацию, историю, отдельные остатки площадок и отсутствие переполнения страницы на ширине 390px.

Миграция применяется через `php artisan migrate`. Рабочие остатки и движения не заполняются автоматически. Фикстуры браузерного складского сценария создаются и удаляются только в тестовой БД.

Итог проверки реализации: 50 backend-тестов, 390 проверок — успешно; TypeScript, production build, ESLint и 3 unit-теста frontend — успешно; оба браузерных сценария (существующий кабинет и отдельный складской цикл) — успешно. Дополнительно проверены UTC-даты движений при PostgreSQL-сессии Europe/Minsk. В рабочей БД после миграции подтверждены нулевые количества строк во всех трёх новых таблицах.

## Интеграция с закупками

Добавлен отдельный модуль [закупок и поставок](PROCUREMENT.md). Его подтверждённые приёмки вызывают StockOperationService с типом receipt, а документ и весь набор складских движений фиксируются одной транзакцией. Сами таблицы остатков и их назначение сохранены; в stock_movements добавлен составной уникальный индекс для внешнего ключа строки приёмки.
